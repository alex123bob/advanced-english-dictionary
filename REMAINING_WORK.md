# Remaining Work

This document tracks follow-up work after the multi-client restructure and starter client implementations.

## Repository Workflow

- Push the current feature branch when ready for remote review.
- Open a pull request from `restructure-multi-client-chrome-extension` after pushing.
- Review generated build outputs locally before release; `dist/` folders remain ignored and should be regenerated by CI or release tooling.

## Native Client Completion

The native clients currently contain source-level starters, not fully generated IDE projects.

### macOS

- Create an Xcode macOS app project or Swift Package wrapper.
- Add the files from `clients/macos-native/Sources/AdvancedDictionaryMac/` to the app target.
- Add app icons, bundle identifier, signing settings, and release configuration.
- Add persistence for recent searches and API settings.

### iOS

- Create an Xcode iOS app project or Swift Package wrapper.
- Add the files from `clients/ios-app/Sources/AdvancedDictionaryIOS/` to the app target.
- Add app icons, bundle identifier, signing settings, and release configuration.
- Add persistence for recent searches and API settings.
- Consider share extension support so selected text from other apps can trigger dictionary lookup.

### Android

- Convert the source starter into a fully verified Android Studio project if this client becomes active.
- Add app icons, package metadata, signing configuration, and release build setup.
- Add persistence through DataStore or Room for recent searches and API settings.
- Consider Android text selection integration through process-text intents.

### Windows

- Create a Windows App SDK / WinUI project and add the Windows starter sources.
- Add `.sln` and `.csproj` files once the chosen Windows app framework is finalized.
- Add packaging, app icons, installer configuration, and release signing.
- Add persistence for recent searches and API settings.

## Shared API Contract

Each client currently has a small local model for the dictionary API response. This is acceptable for scaffolding, but it can drift over time.

Recommended follow-up:

- Add an OpenAPI document or JSON schema for `/api/dictionary` and `/api/dictionary/suggest`.
- Generate TypeScript, Swift, Kotlin, and C# models from the contract.
- Add contract tests with recorded API fixtures.
- Keep the request format consistent across clients: `{ "word": "example", "section": "basic" }`.

## Chrome Extension Polish

- Add extension icon assets and wire them into `manifest.json`.
- Add extension validation in CI, such as checking manifest shape and required assets.
- Revisit broad `<all_urls>` host permissions if deployment/API URLs become fixed.
- Add a settings migration path if extension storage keys change in future versions.
- Consider an inline popup result plus an “open full website” action for selected text, instead of always opening the website from page selection.

## Web Client PWA Polish

The website is installable directly (manifest + service worker in `clients/web/`) rather than through a separate PWA client.

- Add a custom install prompt UX (`beforeinstallprompt`) instead of relying solely on browser/OS install affordances.
- Expand offline support beyond app-shell caching if dictionary data should be available offline.
- Add update prompts when a new service worker version is available.
- Add Lighthouse/PWA checks to CI.

## Web Client Follow-Up

- Keep the existing web build as the canonical full-featured browser experience unless a shared frontend package is introduced.
- Consider extracting reusable API helpers only after multiple clients need the same behavior.
- Add a deployment script update if production deployment still assumes root-level web files.

## Testing And CI

- Add automated smoke tests for the static web (including PWA installability) and Chrome extension builds.
- Add linting/formatting once the repo has chosen cross-client tooling.
- Add CI jobs for `npm run build` and `npm audit --audit-level=moderate`.
- Add native build jobs only after the native starter folders become full IDE/build-system projects.

## Release Readiness Checklist

- Push branch and open PR.
- Confirm production API URL and website URL defaults.
- Add app/extension icons for each shipping client.
- Decide whether native clients remain starters or become fully buildable projects in this repository.
- Add shared API contract generation before expanding API surface area further.
